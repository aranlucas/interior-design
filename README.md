# Roomform

An interior design studio built with TanStack Start + Router, React, Vercel AI SDK, and direct OpenAI image editing. Hosted as one Railway Node service with SQLite on a persistent volume.

Create a room, upload listing/camera photos, collect product photos or IKEA links, select references, and generate or refine a photorealistic visualization — from photos, a 3D guide, or freestyle with no photo at all. Original architecture remains the prompt's authority. Results include history, downloads, brush edits, before/after videos and a before/after slider.

## Secrets

Varlock resolves `OPENAI_API_KEY`, `SESSION_SECRET`, and the OIDC client secret from Bitwarden Secrets Manager. `.env.schema` contains references, never secret values. Supply `BITWARDEN_ACCESS_TOKEN` securely to the process or Railway service. Use a project-scoped machine token. Production uses `varlock run` at boot; secrets are not embedded into the build.

On macOS, save the bootstrap token in your login Keychain once:

```bash
npm run secrets:store
```

Paste the token at Varlock’s masked prompt. Varlock stores it under service `varlock`, account `roomform:local:BITWARDEN_ACCESS_TOKEN`. The tracked `.env.keychain` contains a native `keychain()` reference and is imported only on macOS outside local mode. macOS may ask you to authorize Varlock’s native Keychain access.

The Vite integration loads and validates config for `npm run dev` and `npm run build`; `npm start` resolves secrets at boot through `varlock run`. Keep SSR in `init-only` mode so resolved secrets stay out of build artifacts. Configuration and generated type declarations are defined in [`.env.schema`](.env.schema). On Railway or other non-macOS hosts, supply `BITWARDEN_ACCESS_TOKEN` through the platform's secret environment settings; that value takes precedence over the Keychain resolver. See [Varlock’s macOS Keychain guide](https://varlock.dev/plugins/macos-keychain/) for storage and access management.

`npm run dev:local` skips Keychain and Bitwarden resolution, makes credentials optional, and bypasses login. Production bundles disable that bypass. Unit tests mock `varlock/env` and do not load live secrets.

## Development

Node 24.8+. Install with `npm ci`, then run `npm run dev:local` for a local studio without Bitwarden or login. SQLite data defaults to `.data/`; generation is disabled unless you supply `OPENAI_API_KEY` in your shell. Override `DATA_DIR` or `APP_URL` as needed. When using `tailscale serve`, set `APP_URL` to the exact browser origin (for example, `https://host.tailnet.ts.net:8443`); its hostname is allowed by Vite and mutations require that origin.

For the regular secrets-backed setup, save the bootstrap token in macOS Keychain or supply `BITWARDEN_ACCESS_TOKEN` in the environment, then run `npm run dev`. Validate with `npm run check`, `npm test`, `npm run lint`, and `npm run fmt:check`. Use `npm run fmt` to format and `npm run build` to build.

Photo reconstruction requires **COLMAP 4.x** on the server. On macOS, install it with `brew install colmap`; optionally set `COLMAP_BIN` to an executable path. The existing Railway configuration does not install COLMAP, so provision it in the production container before enabling automatic reconstruction. The app runs sparse reconstruction on the CPU without CUDA; it does not provision dense reconstruction.

Normal tests mock reconstruction jobs. To exercise the real engine with overlapping `.jpeg`, `.png`, or `.webp` photos:

```bash
ROOMFORM_COLMAP_TEST_IMAGES=/absolute/path/to/photos npx vitest run src/lib/colmap-runner.integration.test.ts
```

## Railway

Deploy the repository, mount a persistent volume at `/data`, set `DATA_DIR=/data`, and use one replica. `railway.json` configures build/start and health checks. The app uses SQLite WAL and short synchronous transactions for room changes; image generation happens outside those transactions. Back up the persistent volume before migrating or removing it. Images live as SQLite blobs. Memory-heavy generation, brush edits, and reconstruction share one server-wide processing slot. Image inputs have a 32 MB aggregate budget checked from SQLite blob lengths before loading. Variations use serial single-image provider calls and are saved one at a time. See the [memory investigation](docs/image-memory-investigation.md) for evidence and remaining limits; the current production service has a 1 GB ceiling, and 500 MB is not a supported capacity claim.

## Working with room photos and 3D guides

Open **3D room → Build 3D room** to reconstruct overlapping photos with COLMAP. Use several closer angles of the same unchanged room, with details visible in multiple photos. The result is a sparse, partial cloud of colored points and recovered camera positions, with gaps on blank walls and unseen areas. It has no known physical scale and is not a solid mesh or measurement tool. No OpenAI key or external image service is needed.

If alignment fails, **Help match photo details** accepts at least 12 distinct corresponding points in a pair of photos, using pointer or keyboard input. Matches undergo geometric verification and do not guarantee reconstruction. **Use a manual layout** offers an editable photo-covered rectangular room as a fallback. **Create AI finish** generates a separate 2D image with inferred areas labeled; it does not add measured geometry.

For a solid approximate model, choose **AI-assisted → Build AI room layout**. It sends up to eight room photos, spread across the full upload sequence, to OpenAI vision with `store: false` and requires `OPENAI_API_KEY`. The model estimates walls, openings, fixtures, large furniture and surface material categories, then reviews the draft against the original photos in a second vision request. Saved room measurements guide scale when unambiguous. Both requests use high reasoning effort; the second pass adds latency and API cost. Local checks reject invalid outlines, overlapping openings, floating doorways, furniture outside the footprint (including rotated boxes) and elements above the ceiling. Inferred surfaces appear amber; even photo-visible elements have estimated positions and dimensions. The preview uses material-specific roughness, generic wood/tile floor patterns and shaped sofas, beds and tables. These are approximate renderings, not recovered photo textures. Existing saved layouts remain readable without material or camera fields. The model also estimates where each photo was taken (position, height, direction, field of view, using the 35 mm-equivalent focal length as a hint when present; the browser reads it from EXIF before upload compression strips metadata) and the left-to-right order of fixtures in each photo. When that perceived order strongly contradicts the estimated positions, the plan is mirrored automatically and the change is listed in assumptions. Camera estimates are AI guesses, not recovered poses; the mode recovers no depth maps. `OPENAI_ROOM_LAYOUT_MODEL` overrides the layout model (default `gpt-6.1-sol`).

The 3D view offers **View from photo N** presets, an **Eye level** preset, a field-of-view slider, and a ceiling that appears only while the camera is inside the room. **Edit layout** lets you select, drag, rotate and delete fixtures, mirror the plan, rescale the whole estimate from one measured wall, and place product references as colored boxes at their confirmed size. Saved edits replace the build's stored layout after the same validation as an AI build; capture is disabled until edits are saved or discarded. API work runs remotely; local rendering needs no CUDA, model weights or COLMAP.

Build status survives reloads. One memory-heavy job runs at a time per server, with a 12-minute deadline for reconstruction; COLMAP uses four CPU threads. Cancellation stops its child process and removes temporary images and feature databases. A failed rebuild keeps the previous successful result; changed input photos mark it outdated. After a server restart, the next status request marks an interrupted build failed so it can be retried.

For AI layouts, **Capture this view → Generate this view** sends a clean JPEG of the chosen 3D camera as the first image, followed by the original source photos in evidence order, selected references, and an optional prior design. The prompt describes the saved layout in prose and lists where each wall opening, fixture and placed product falls in the captured image, projected from the saved camera in code, rather than sending raw coordinates. Eye-level interior captures are rendered as interior photographs; elevated and cutaway captures keep their composition. Placed products are mapped to their reference images, and their photos are sent automatically. The capture supplies camera/layout; source photos supply appearance evidence. This replaces the photo-only layout pre-pass, but does not guarantee adherence or physical fit.

Each guided design retains its guide and validated layout snapshot after reconstruction rebuilds. **Compare** shows guide versus design; **3D guide and source evidence** exposes retained constraints. Deleting the design removes those artifacts. Ownership, current reconstruction, source photos and capture dimensions are validated at generation: changed photos or a running/replaced build require rebuilding and a fresh capture. **Generate from photo** remains available.

Stored AI layouts use plan coordinates (+x right when facing +z). [`toSceneLayout`](src/lib/ai-room-layout-geometry.ts) converts once to Three.js coordinates, including fixture rotation and wall openings; stored evidence must retain its original convention to avoid mirrored geometry.

## Image generation

Modes are **Redesign** (restyle/refurnish while preserving architecture), **Stage** (furnish an empty room), **Paint** (change colors and finishes only), **Empty** (remove movable furniture), **Sketch** (render a drawing or 3D screenshot), and **Freestyle** (compose without a photo). Outdoor room types preserve fixed structures, boundaries, paving and permanent plantings. Optional people/pets and lighting controls affect the scene. Designs support history, starring, downloads, brush edits, a comparison slider and client-side before/after video export.

**Image settings** saves quality and size per room. Current defaults and supported choices live in [`image-settings.ts`](src/lib/image-settings.ts); `OPENAI_IMAGE_MODEL` overrides the model. The default is `gpt-image-2.6-sunburst` for detailed generation and editing, verified against the [OpenAI image generation guide](https://developers.openai.com/api/docs/guides/image-generation) on November 5, 2026. New rooms draft at Medium quality and **Match photo** framing, so a portrait or 4:3 photo is never recomposed to 16:9. **Render final** (the sparkle action on a design) re-renders that design alone at Max quality and the largest size for its aspect ratio, keeping its content unchanged. PNG output and existing sizes are retained. Complexity uses the API default (`high`). Prompts follow the [GPT Image 2.6 prompting guide](https://developers.openai.com/api/docs/guides/image-prompting): separate requested edits from preservation constraints, retain source camera and product identities, and treat estimated plans as subordinate to source evidence and confirmed measurements. Outputs above `2560x1440` are experimental. **Match photo** and captured 3D guides preserve source aspect ratio within API pixel limits; freestyle uses its orientation choice. Designs record requested model, quality and size, plus the full prompt sent to the image model (shown under the design's details) for debugging and evaluation. Prompts are stored as separate objects, one per run and shared by its variations, so the per-user room data that status polls re-read stays small. Filmstrips show a stored 640 px JPEG preview that the browser makes once from each design; the full PNG is used on the stage, for downloads, and for brush edits. Single-image runs also record reported output-token usage; displayed image-output cost uses the documented $30 per million output tokens for GPT Image 2.5 and 2.6 Sunburst/Flare and excludes input tokens. Transient rate limits retry twice with backoff, while exhausted credits stop immediately. Brush edits keep the source design's size and quality, can include up to four references (sent after the design image), record usage and cost, and use the same retries.

Runs request 1, 2, 4 or 8 variations using serial single-image provider calls. Each image records its own reported usage and cost. This repeats input billing per variation and takes longer than a batched call. If any variation fails, the whole job fails and intermediate media are removed; completed provider calls may still be charged. A per-user lease and a server-wide processing slot remain held until settlement, including cleanup. Busy requests return 409 before image loading, rather than joining an in-memory queue. The [memory investigation](docs/image-memory-investigation.md) records evidence and remaining capacity limits.

Room measurements and editable product dimensions guide scale; client-supplied room measurements take precedence over estimates. Redesign and Stage generations with at least one product reference first attempt a structured vision placement plan (`OPENAI_LAYOUT_MODEL`), falling back to prompt-only guidance on failure (failures are logged). Other modes, outdoor rooms and captured AI layouts skip that pre-pass. Empty mode sends no reference images; Paint mode treats references as color and material swatches only. Product sizes are related to familiar objects (door widths, counter and door heights), and with room measurements, to each measured side, since the target wall is unknown.

To compare prompt changes, `src/lib/generation-eval.integration.test.ts` runs a case file through real generation and a vision-model judge, writing images, prompts and scores per label. It is skipped unless `ROOMFORM_EVAL_CASES` and `OPENAI_API_KEY` are set, and every run is billed; see the file header for the case format. Pixel dimensions are never physical measurements, and AI output does not guarantee product fit.

Product import reads metadata and images from public HTTPS pages, including Shopify variant images and size choices. Confirm or edit imported dimensions before generation. Requests reject non-public IP ranges, pin validated DNS results and recheck redirects. Pages that block access or require JavaScript need an uploaded photo; there is no automatic Zillow import or general web scraper.

## Reliability validation

See [the behavior audit](docs/reliability-audit.md) for findings and scope. CI runs the existing checks/tests, a production build without external secrets, a negative control proving the targeted regressions fail on the audited baseline, and `npm run test:e2e` using published `e2e` and its web engine. The browser journey creates a room, autosaves a brief, renames it, verifies persistence after reload, and deletes it. It uses an isolated `.data/e2e` SQLite database and the existing development auth bypass; no model calls or provider credentials are required. Baseline logs and browser failure evidence are uploaded as CI artifacts. Tests and builds for this audit run only in CI.
